# 0032. Official Jev API decider and the OpenRouter Jev Router as a virtual model

**Status:** Accepted (2026-11-11), implements PLAN-v0.3 R9 and decision D9. **Owner review** (first real calls).

## Context
The owner holds an account for TypeSafe's hosted Jev API; no key was available while this was built, and the project budget allows no paid or unpriced calls. Both integrations were therefore built strictly from the official documentation, read on 2026-11-11: https://docs.typesafe.ai/api and https://openrouter.ai/docs/guides/routing/routers/jev-router.

## Decision
- **Official Jev API** = decider kind `jev_official` on the shared protocol client (ADR 0030). Defaults: endpoint `https://api.typesafe.ai/v1/systemone`, model `jev-latest` (the reference also shows `jev-preview`; `GET /v1/models` lists the rest); both are editable settings. Key in the credential store (Bearer token), never returned or logged. Default clearance `public`, configurable up to min(internal, `ERAG_CLOUD_MAX_CLASSIFICATION`), never confidential. Price: the reference only says input tokens are billable and output tokens are currently free, with no figure; the decider defaults to the third-party figure of 0.042 USD per million input tokens (flagged "unverified default" in the panel), editable; the cost recorded is `usage.input_tokens x price` since the response has no cost field. Daily cap 100 and monthly budget 0.01 USD by default (raise to spend the planned EUR 1). The **Test** button makes one minimal real call and reports latency, tokens and cost. Real tests are opt-in (`decider_official`, `ERAG_TEST_JEV_API_KEY`).
- **Where the docs differ from the plan.** (1) The plan said the official API might also be reachable through OpenRouter: OpenRouter documents only the Jev *Router* (a model that routes and serves), not the `/v1/systemone` decision API, so a key issued by OpenRouter cannot be used as a decider; the configurable endpoint still allows any gateway that exposes `/v1/systemone`. (2) The Jev Router options are not request fields of their own: they go in a top-level `plugins` array as `{"id": "jev-router", "cost_tier": "low"|"medium"|"high", "allowed_models": [...], "excluded_models": [...]}` (also an alias `models`, not exposed); unknown fields are refused with HTTP 400, so they are validated on save. (3) No price or per-request price cap is documented for the Jev Router; a cost tier is a preference only.
- **OpenRouter Jev Router** = the model id `typesafe/jev-router` added to the built-in OpenRouter provider (a "virtual model": OpenRouter picks and serves a model of its catalog). New per-model columns (migration 0011): `max_classification` (a model may only **lower** its provider's clearance) and `options` (the plugin options, step-up to change, audited). The Jev Router model defaults to **public** because it evaluates the whole conversation. Its requests ask for `usage.include` (OpenRouter reports the real cost) and are bounded by the OpenRouter budgets, `max_tokens`, the request cap and quotas; its price is unknown to the worst-case check unless the admin enters one (the panel says so and recommends a low ceiling and an allowed list of models with known prices).

## Consequences
- **Untested against the real services tonight**: the official API (no key) and the Jev Router (no unpriced calls). Tested: request building and response parsing against the documented shapes, the plugin payload observed at the egress hook (blocked there), the public default clearance, the per-model clearance cap and step-up (`tests/security/test_jev_router.py`, `tests/security/test_model_router.py`).
- The served model of a Jev Router answer is not recorded separately (usage is recorded under `typesafe/jev-router`); OpenRouter's `X-OpenRouter-Metadata` pipeline details are not requested.
