# 0021. MCP registry for remote servers and the clearance model

**Status:** Accepted (2026-11-09), implements PLAN-v0.2 sections 3 and 4 and R4 (decisions D1, D2, D7; owner confirmed the clearance model and `result_classification = confidential` by default)

## Decision
- **Registry.** `mcp_servers` gains `builtin`, `transport` (`stdio` | `http` | `runner`), `url`, `status` (`pending` -> `approved` -> `disabled`), `auth_secret` (a vault secret sent as a bearer token, audited as `mcp:<id>`), `max_classification`, `result_classification`, `send_permission_context`, `limits` (timeout, per-tool rate limit across users, max result bytes) and `runtime` (R5). Tools gain `content_hash`, `approved_hash`, `needs_review`, `review_reason` and `arg_constraints` (migration 0007). Built-in servers keep their behaviour (ADR 0010).
- **Defaults for a new registration:** `status = pending`; every discovered tool disabled; `max_classification = public` (nothing internal is sent unless the admin raises it: the most restrictive choice, not fixed by the plan); `result_classification = confidential` (owner decision); `send_permission_context = false` (a third-party server has no use for our signed scopes and should not learn them).
- **Clearance, filter before send.** A registered server is an external recipient, like a cloud model. When the conversation's effective classification is above the server's `max_classification`, its tools are not offered, and a call (the classification can rise mid-loop) is refused with "tool unavailable"; the refusal is what the model sees and it is audited with the classification.
- **Label after receive.** Everything a registered tool returns is labeled with the tool's classification (initialised from `result_classification`, editable per tool) and goes through the existing validator; the router then keeps the rest of the conversation on models cleared for that label (ADR 0003). We cannot filter third-party output per user (known boundary).
- **Tools are discovered, not trusted.** Registration calls `tools/list`. Enabling a tool records the hash of its name, description and schema as `approved_hash` (step-up required). On every call the gateway lists the tools in the same session and compares the live definition with `approved_hash`; on a mismatch (or if the tool disappeared) the tool is disabled, flagged for review, audited (`mcp.tool.changed`) and the model is told it is unavailable. "Rediscover" reports new/changed/removed tools; changed approved tools are disabled.
- **Descriptions are untrusted text.** Control and bidi characters and markup are removed, length is capped (1,000 characters; 300 for schema descriptions), and a description that matches the injection heuristics is withheld from models entirely and flagged for review. Tool names must be valid function names; schemas are capped at 16 KB.
- **Argument constraints** per tool argument: `enum`, `pattern`, `minimum`, `maximum`, `max_length`, `force`. Forced arguments are removed from the schema the model sees and set by the gateway; the others are shown to the model as schema hints and enforced before the call; the final arguments are validated against the server's schema.
- **Unapproved tools look unknown.** A tool of a pending server, or a tool that is disabled or under review, gets the same "unknown tool" refusal as a non-existent one, even for a role that holds the grant. The old built-in tools endpoint refuses registered tools so the review cannot be bypassed.
- **Transport.** Streamable HTTP through the MCP SDK with an `httpx2` transport that applies the SSRF guard of ADR 0020 (public addresses only unless `ERAG_SSRF_ALLOWLIST`, IP pinning, TLS verified, redirects only same-origin by the SDK). The reference servers gained `--http` and `--uds` (Unix socket) so the same scoping tests run over stdio and HTTP.

## Consequences
- The demo Compose file runs `mcp-office` (a demo "third-party" server) and the seed registers it as pending; approving it is an admin task.
- An extra `tools/list` round trip per call to a registered server (the price of rug-pull detection).
- Per-call MCP sessions (no pooling); acceptable for the demo scale.
- Tests: `tests/security/test_mcp_registry.py` (real office server and a real "mutable" server restarted with a poisoned description; reference tickets server over HTTP).
