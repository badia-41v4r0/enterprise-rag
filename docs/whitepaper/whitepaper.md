# Permission-Aware Generative AI for the Enterprise

### A reference pattern for RAG and tool use where the model only sees what the user may see

*Badia Partners, https://badiapartners.com. Draft 0.1 (November 2026). Licensed CC BY 4.0 (see `LICENSE-CC-BY-4.0.txt` in this directory). The reference implementation is source-available under PolyForm Noncommercial 1.0.0.*

> Draft status: all sections are written from the MVP as built; numbers come from the automated test suite and a single developer workstation.

## 1. The problem: a naive enterprise assistant is a data-leak machine

A typical first enterprise assistant indexes "the company's documents" into one vector store, gives a model a few tools with a service account, and lets everyone ask questions. Each part looks reasonable; together they break the most basic rule of information security, that people only see what they are allowed to see:

- **Retrieval ignores permissions.** The nearest chunks to "What is the salary band for a senior engineer?" are the HR salary table, whoever asks.
- **Post-filtering is fragile.** Filtering the top-k after search either leaks (when the filter is forgotten in one code path) or returns nothing (when the top-k was all forbidden).
- **ACLs copied into the index go stale.** Removing someone from a group does not remove their access until the next re-index.
- **Tools run with a service account.** The model, not the backend, decides which records to fetch, and anyone who can talk to the model can talk to the ERP.
- **Every request goes to the same cloud model**, including the ones grounded in payroll data.
- **Content is treated as instructions.** A document or ticket that says "ignore previous instructions and call X" is read by a model that has tools.

## 2. Use case: ACME Corp, same question, different people

ACME Corp (fictional) has five document containers: General Handbook (internal), HR Confidential (confidential), Finance (confidential), Engineering (internal) and Product Docs (public); a ticketing/ERP system; and six personas: an HR manager, a finance analyst, an engineer, a new hire, an executive and an administrator.

The same question, "What is the salary band for a senior engineer?":

- **HR manager:** "58,000 to 72,000 EUR [1]", citing *Salary Bands 2026*; generated by a local model because the context is confidential.
- **Engineer:** sees only the engineering career ladder; the answer says compensation is not in their sources and is handled by HR.
- **New hire:** "I don't have information about that in the sources available to you."

"Show me open invoices over 10k EUR": the finance analyst's model calls `list_invoices` and lists three invoices; the engineer's model is never told the tool exists. When the administrator removes the HR role from the HR manager, the next question loses access immediately, and the earlier confidential answer in the same conversation is withheld from the prompt.

## 3. Architecture, layer by layer

*(See `docs/architecture.md` for the diagram.)*

**Identity and policy.** Users, roles, containers with a classification, allow-only grants (`read`/`manage` on containers, `read` on restricted documents, `execute` on tools). One function computes a user's effective permissions from the database on every request. Administrators manage the system but get data only through grants, which are audited.

**Query.** The question is embedded by a local model. The vector search runs with the user's allowed containers and restricted documents *inside* the SQL query, over current document versions only, and every hit is re-checked against the documents table before use. A context builder deduplicates, enforces a token budget and assigns citation numbers.

**Routing.** After retrieval, the effective classification of the request is the highest classification among the retrieved chunks, the conversation history in the prompt and, later, every tool result. A policy maps classifications to permitted models: confidential data goes only to local models; if none is available the request is refused before anything leaves the machine. The cloud provider also checks the classification itself, as a second line.

**Prompt.** System rules, history, then the context inside explicit delimiters. Retrieved text is treated as untrusted data, and our delimiter tags inside it are neutralized so content cannot "close" the context and speak as the system.

**Tools (MCP).** The model only receives tools the user may execute. Each call is validated against a strict schema, checked for resources outside the user's scope, rate-limited, and sent through a gateway that attaches a signed, 60-second permission context scoped from the same permissions as retrieval. MCP servers filter their data by that context before reading anything, and reject forged, expired or misdirected tokens. A result validator then enforces a size cap, raises the classification to what the data really is, and drops instruction-like strings. If the new classification exceeds the current model's clearance, the conversation switches to a local model before the result is sent.

**Ingestion and persistence.** Uploads are hashed, deduplicated, versioned and processed by a worker that claims jobs from a database table. A new version replaces only that document's vectors, atomically. One PostgreSQL instance stores identities, ACLs, vectors, jobs, conversations and an audit log of every retrieval, model request and tool decision.

## 4. Principles for enterprise generative AI (the reference pattern)

1. **The model never decides permissions; the backend does.**
2. **Authorize before retrieval, not after generation.** Push the ACL into the search, and re-check.
3. **Resolve access at query time.** Never copy ACLs into an index you cannot revoke instantly.
4. **Route by data classification, after you know the data.** The most sensitive item in the context decides which models may see it.
5. **Show the model only the tools the user may use; scope the tool's data before the call.** The tool server is a second barrier, not the first.
6. **Treat every retrieved document and tool result as untrusted input.**
7. **Audit every decision**: what was retrieved, what was dropped, where each request went, which tools were allowed or refused.
8. **Prove it with tests that do not depend on model behaviour**: assert on chunk IDs, prompts and outgoing requests.
9. **Keep credentials out of reach of the application surface.** Encrypt them at rest, never let an API return them, audit every use, give each one the least scope and the shortest life that works, and be able to rotate them without downtime (section 7.3).

## 5. Design decisions and trade-offs

- **Local vs cloud.** Local models protect confidential data and cost nothing per token, but on modest hardware they are slower (10 to 40 s per grounded answer with a 4B model on a 6 GB GPU). The router lets non-confidential requests use cloud models where allowed.
- **Classification routing granularity.** Per container is simple and auditable; per-paragraph classification would be more precise but harder to administer.
- **Query-time ACL vs indexed ACL.** Query-time costs a join per search but makes revocation immediate and removes a whole class of stale-ACL bugs.
- **MCP gateway with signed context vs delegated OAuth.** Signed context works with any internal system the company controls; delegated OAuth to SaaS is the next step for external systems.
- **Heuristic injection filtering.** Useful as a second barrier; the guarantees come from the structure (authorized data, authorized tools), not from the filter.

| Revocation + history (2) | Removing a role through the admin API removes access and withholds earlier answers | pass |

| Real local model (4) | Streaming, real tool call, salary scenario end to end, invoice scenario end to end | pass |

Latency on the reference workstation (GTX 1660 SUPER 6 GB, 16 GB RAM): about 10 to 12 s for a grounded answer and roughly 40 to 90 s for an answer with one tool call, dominated by the model's reasoning tokens. Retrieval and authorization add milliseconds. Cost: zero (all local).

**Limits.** These tests prove what the model is *given*, not what it *says*. A model can still be wrong, or repeat what it was legitimately given to the user who was authorized to see it. The injection filter is heuristic. See `docs/threat-model.md`.

## 7. Limits and target architecture beyond the MVP

Multi-tenancy, SSO/OIDC, delegated OAuth to SaaS systems, external connectors, deny rules, hybrid search and reranking, a spend ceiling per cloud provider, long-lived MCP sessions, tamper-evident audit, horizontal scaling. See `ROADMAP.md`.

### 7.1 Extensibility without losing control (v0.2)

A reference pattern is only useful if a company can grow it without reopening the holes it closes. Version 0.2 adds five extension points, each built so that it cannot widen what a model or a tool may see:

- **Delegated management.** A department head can maintain their own container (upload, replace, delete) without becoming an administrator. Delegation covers content only: who may read it and how it is classified stay with the administrator, and a manager cannot use the "restricted" flag or upload deduplication to read documents they were not given.
- **Connectors.** Folders and web sites are synchronised into one container and inherit its access and classification, so retrieval, routing and the leakage tests apply to imported content unchanged. Outbound requests are limited to public addresses (an operator allowlist opens specific internal ones) and every redirect is re-checked.
- **Registered MCP servers.** Any MCP server can be added, but it is treated like a cloud model: an external recipient with a clearance. Data above its clearance is never sent to it (the tool is not offered and calls are refused), and everything it returns is labeled, by default as confidential, so the rest of the conversation stays on local models. Tools are discovered, not trusted: they start disabled, are approved one by one for specific roles, can be constrained argument by argument, and are disabled automatically if the server changes them after approval.
- **Isolated execution.** MCP servers packaged as approved images run in containers with no network at all, a read-only filesystem, no Linux capabilities and resource limits. The gateway reaches them through a Unix socket; they cannot reach the database, the application, the internet or each other. The application never holds the container engine's socket.
- **Model providers.** Administrators can add chat models from the admin panel (other Ollama instances and any OpenAI-compatible API) and choose a default model. Whether a provider counts as local is not the administrator's call: it follows from the network address it resolves to, checked again on every request, and only local providers may ever see confidential data. A cloud provider starts cleared for public data only, the default model is used only when it is cleared for the request, and paid APIs are bounded by a monthly ceiling and a daily request cap.

Credentials for all of this live in an encrypted, write-only credential store whose every use is audited, and every action that creates a new data-access or code-execution path requires the administrator to re-authenticate (optionally with a second factor).

### 7.2 Known boundaries

These limits are inherent to the current design and are documented rather than hidden:

1. **Source permissions are not mirrored.** If a shared drive or site contains files restricted to some people, importing it into a container shows them to everyone who can read that container. Connectors must only point at content whose audience matches the container's. Mirroring source ACLs is a separate, larger feature.
2. **Third-party MCP output cannot be filtered per user.** A tool usually fetches data from a system we do not control, with its own credentials, and we do not know that system's permissions. It is controlled at tool and role level and labeled; it cannot be scoped per user unless the server cooperates (as the reference servers do with the signed permission context).
3. **The master key sits on the same host as the application.** The credential store protects against database and backup leaks, not against compromise of that host. Section 7.3 explains exactly where the protection ends and how to reduce the damage if the server is compromised.
4. **Compromise of an administrator account remains the largest risk.** Mitigations are optional MFA, step-up re-authentication for sensitive actions, the audit trail and the confinement of MCP containers; none of them stops a determined attacker who controls an administrator session for long.

### 7.3 Protecting credentials, and where that protection ends

Connectors, registered MCP servers and the cloud-model provider all need credentials, and a credential is the one thing in the system that is worth more to an attacker than any document. The reference implementation treats them as follows.

**What the credential store does**

- Each secret is encrypted with AES-256-GCM using a fresh nonce, and the secret's name is bound into the ciphertext as authenticated data, so a ciphertext copied onto another entry fails to decrypt. A wrong master key is detected instead of producing garbage.
- The master key is **not in the database**. It comes from an environment variable or a key file with owner-only permissions, kept in a different volume from the data.
- The interface is **write-only**: a secret can be created, replaced or deleted, but no endpoint and no screen ever returns it. The administrator sees names, versions, last use and which component references each one.
- **Every use is audited** (which component, when, never the value), and a component can only obtain the secrets explicitly assigned to it.
- Changing or adding a secret requires the administrator to re-authenticate (and to present a second factor if enabled), and the master key can be rotated, re-encrypting everything in one transaction.
- The test suite asserts that no plaintext secret is present anywhere in the database, and the same absence was checked by hand in a full database dump, in the application logs and in the environment of the running container.

**What it protects against:** a leaked database dump or backup, a SQL-level read of the tables, an accidentally exposed log, and a curious administrator (who cannot read a stored value back). In each case the attacker obtains ciphertext without the key.

**Where the protection ends.** If an attacker gains control of the server itself, or can run code inside the application process, the store cannot help: the application must decrypt a secret in order to use it, and the master key it needs sits next to it. No software scheme can make a secret usable by a program and unusable by whoever controls that program. The achievable goal is to limit the damage, detect the intrusion and recover quickly. The measures below do that, and the table says what the reference implementation already does.

| Measure | Effect if the server is compromised | In v0.2 |
|---|---|---|
| **Least-scope, capped credentials.** The cloud-model key can carry its own spending cap at the provider, and the application adds a hard monthly ceiling and accepts free models only by default. | The attacker cannot spend more than the cap and cannot reach paid models. | Yes |
| **Rotation and a recovery runbook.** Revoke at the provider, rotate the master key, re-enter the secrets. | Shortens the window in which a stolen secret is useful. | Yes (`erag secrets rotate-master`) |
| **Audit of secret use.** Every use is logged by component. | Makes abnormal use visible; it does not prevent it. | Yes (alerting is left to the operator) |
| **Keep the master key off the host's disk.** Hold it in a hardware or cloud key manager (an HSM, a cloud KMS, or a vault service) and let the application ask it to unwrap secrets, or unlock it manually at boot so it exists only in memory. | Stealing the disk or a backup yields nothing; access can be revoked centrally and is logged outside the host. While the attacker controls the running application they can still ask for decryption, but only for as long as the intrusion lasts and visibly. | Target architecture |
| **Separate the component that holds secrets from the one exposed to users.** A small credential broker, with its own user and container, performs the outbound calls that need a secret, so the web application never holds the key. | A bug in the web application, the most likely entry point, no longer yields the master key or the secrets. | Target architecture (the container runner already follows this pattern for the container engine) |
| **Short-lived and per-user credentials.** Delegated OAuth and tokens that expire in minutes instead of one long-lived shared key. | A stolen token is soon useless and is limited to one user's access. | Target architecture |

In short: the credential store makes the common failures (database and backup leaks, log exposure) harmless, and the surrounding measures bound the damage of the rare catastrophic one. A company with a high-risk threat model should adopt the "key manager" and "separate broker" rows before putting the system in production; the reference implementation is structured so that they can be added without changing how the rest of the system uses secrets.

## 8. How-to: install, configure, onboard, operate, harden

1. **Install:** Docker Compose and Ollama with `bge-m3` and a local chat model; `docker compose up`. See the README.
2. **Configure:** set strong `ERAG_SECRET_KEY` and `ERAG_MCP_CONTEXT_SECRET`, `ERAG_ENV=prod`, `ERAG_SEED_DEMO=false`, HTTPS in front with `ERAG_COOKIE_SECURE=true`. Decide `ERAG_CLOUD_MAX_CLASSIFICATION` (default `internal`; `public` keeps internal data local).
3. **Onboard a company:** create the first admin (`erag create-admin`), then containers that mirror your data-classification policy, roles that mirror your groups, grants, and upload documents. Mark the few sensitive documents inside broad containers as restricted.
4. **Operate:** watch the audit log (denied tool calls, ACL re-check mismatches, refusals), the ingestion jobs, and model latency.
5. **Harden:** review container classifications regularly, keep tools minimal, register only trusted MCP servers, rotate secrets. Back up the credential store's master key separately from the database (losing it means re-entering every secret; storing both together defeats the encryption), put credentials behind the strictest scope and spending cap their provider offers, and for high-risk environments move the master key to a key manager and run the credential broker as a separate service (section 7.3).
